# NetKKC 仕様

API の仕様（エンドポイント、要求・応答の形式、上限値、エラー）は `openapi.yaml` で定義する。
本書には、`openapi.yaml` では表せない方針と今後の検討事項だけを書く。

## 目的と範囲

NetKKC は、組み込み・エッジデバイス向けに、Mozc によるかな漢字変換を
ネットワーク経由で提供するサーバーである。

- 初期の通信方式は HTTP/HTTPS とし、将来は通信方式を差し替えられる構成にする。
- 文節の自動分割と候補生成はサーバー側で Mozc を利用して行う。
- 初期実装では固定辞書を利用し、学習は行わない。

## 方針

- 変換状態（文節の区切り・確定状態）はクライアントが保持する。サーバーは要求間の状態を保持せず、
  前回の要求・応答との一致も検証しない。
- 読みは加工せずに Mozc に渡す。正規化（結合濁点の合成、半角・全角の変換など）は行わず、
  分解された読みなどを送った場合の結果はクライアントの責任とする。
- 応答の文節の読みは Mozc が返した読みとし、クライアントは以後の再変換でそれを基準にする。
- API の変更は `openapi.yaml` を修正し、`make generate` でコードを再生成して反映する。

## 候補の段階的な取得（予定）

初期実装は、組み込み機器の通信コスト（往復回数・TLS の接続確立）を優先し、
1 回の要求で文節の区切りと候補（`max_candidates` 件まで）を返す。
1 回の応答では機器が受け取りきれない場合に備えて、次の 2 パスの変換を追加する予定とする。

1. 1 パス目: `max_candidates: 0` で変換する（有効範囲を 0〜1000 にする）。
   応答には文節ごとの照会用キーを含める。
2. 2 パス目: クライアントは必要な文節の候補だけを、`GET /candidates/{key}` で照会用キーを使って取得する。
   応答はページング付きとし、受け取れる量ずつ取得できるようにする。

照会用キーは UUID とし、文節の候補を期限付きで Redis に保存してキーで引く。
実装時に Compose へ Redis を追加する。

保存した候補は期限が切れると消える。期限切れと存在しないキーは区別できないため、
どちらも 404 とする。クライアントは 404 を受け取ったら、手元の文節の区切りで
`/reconvert` を送り直し、新しい照会用キーを受け取る。

追加の時期は、実機で初期実装を使ってから判断する。次の点は未確定とする。

- ページングの形式。
- 保存期間と、期限をクライアントに知らせるかどうか。
