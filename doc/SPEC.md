# NetKKC 仕様

## 目的と初期実装の範囲

NetKKC は、組み込み・エッジデバイス向けに、Mozc によるかな漢字変換を
ネットワーク経由で提供するサーバーである。

- 初期実装は変換 API 1本から始める。
- 初期の通信方式は HTTP/HTTPS とし、将来は通信方式を差し替えられる構成にする。
- サーバーは単一の読み文字列を受け取り、文節の配列と文節ごとの変換候補を返す。
- 文節の自動分割と候補生成はサーバー側で Mozc を利用して行う。
- 変換状態はクライアントが保持する。NetKKC は要求間の状態を保持しない。
- 初期実装では固定辞書を利用し、ユーザー別の学習や確定通知用の独立 API は設けない。
- ヘルスチェックは変換 API とは別に提供する。

## API 定義とコード生成

- API 定義は `openapi.yaml` に OpenAPI 3.1 形式で記述する。
- API モデルとサーバーひな型は、この定義から `oapi-codegen` で生成する。
- `make generate` で oapi-codegen v2.8.0 と `oapi-codegen.yaml` を使用し、
  `internal/api/openapi.gen.go` にモデルと Echo サーバーインターフェース（ルーティングを含む）を生成する。
- 既存の Echo 構成に合わせたサーバーインターフェースを生成し、変換処理は別に実装する。
- 生成コードの手編集ではなく、定義の修正と再生成で API の変更を反映する。
- 初回変換と再変換は `POST /convert` で処理する。
- 入力全体と文節の読みの一致などの検証は、
  生成されたモデルやサーバーインターフェースだけでは保証されないため、別途実装する。

## ヘルスチェック

`GET /healsh` は次の応答を返す。パスは `/healsh` とする。

- ステータス: HTTP 200
- Content-Type: `text/plain`（charset の付記は許容）
- 本文: `OK`

ルート `/` に挨拶用エンドポイントは設けない。

## 読みの扱い

サーバーは読みを加工せず、そのまま Mozc に渡す。
正規化（結合濁点の合成、半角・全角の変換など）は行わない。
結合濁点（U+3099）などで分解された読みを送った場合の変換結果は、クライアントの責任とする。

応答の読みは Mozc が返した読みとする。Mozc は入力を書き換えることがあり
（例: 全角英数字 `ＡＢＣ` は半角 `ABC` になる）、その場合は要求の読みと一致しない。
クライアントは以後の文節操作・再要求で、応答の読みを基準にする。

## 変換要求

初回は `POST /convert` に単一の読み文字列を JSON 本文として送る。
Content-Type は `application/json` とする。

```json
{
  "reading": "きょうはとうきょうにいく"
}
```

| フィールド | 意味 |
| --- | --- |
| `reading` | 変換対象全体の読み文字列。必須。 |
| `segments` | クライアントが指定する文節の配列。省略または空配列なら自動分割する。 |
| `max_candidates` | 未確定文節ごとに返す候補の最大数。1〜1000。省略時は 20。 |

初回の文節分割はサーバー側で行う。クライアントによる事前の分割は要求しない。

## 変換応答

Mozc が返した読みと、各文節の読み・変換候補を返す。
以下の文節と候補は構造を示す例であり、Mozc の実際の分割・候補順を保証しない。

```json
{
  "reading": "きょうはとうきょうにいく",
  "segments": [
    {
      "reading": "きょうは",
      "confirmed": false,
      "candidates": ["今日は", "教派"]
    },
    {
      "reading": "とうきょうに",
      "confirmed": false,
      "candidates": ["東京に"]
    },
    {
      "reading": "いく",
      "confirmed": false,
      "candidates": ["行く", "逝く"]
    }
  ]
}
```

## 再変換と文節単位の確定状態

クライアントは文節境界や確定状態を変更し、同じ変換 API に再要求する。
文節の伸長・縮小や確定のために別の API は設けない。
先頭から順に確定する制約は設けず、途中・末尾の文節だけを確定してよい。

文節の属性は次のとおりとする。

| フィールド | 意味 |
| --- | --- |
| `reading` | その文節の読み。 |
| `confirmed` | 確定済みかどうかを示す真偽値。省略時は `false`。 |
| `candidates` | 変換候補の文字列配列。確定済み文節の再送時は、確定した候補1件だけを入れる。 |

再要求の例:

```json
{
  "reading": "きょうはとうきょうにいく",
  "segments": [
    {
      "reading": "きょうは"
    },
    {
      "reading": "とうきょうに",
      "confirmed": true,
      "candidates": ["東京に"]
    },
    {
      "reading": "いく",
      "confirmed": false
    }
  ]
}
```

- `confirmed: false` または省略: 未確定として、読みと指定された文節境界から
  候補を生成し直す。クライアントが `candidates` を送っても、再変換には使用しない。
- `confirmed: true`: 確定済みとして、文節の読み・境界と確定候補を維持する。
  クライアントは候補一覧全体を再送する必要はなく、確定した候補1件だけを返す。
  候補が0件または複数件なら入力エラーとする。
- 候補が1件でも、`confirmed: true` がなければ確定済みとはみなさない。
- 確定解除は、クライアントが `confirmed` を `false` にするか省略して再要求する。
- 確定文字列のために別の `text` や `fixed_text` フィールドは設けない。
  フラグ名は `confirmed` とし、`fixed` は使わない。

応答でも確定済み文節は `confirmed: true` と確定候補1件を保持し、
その文節について新たな候補一覧を生成しない。

## ステートレス性と入力の検証

サーバーは、前回の要求・応答との一致を検証しない。
読みが前回とまったく違っていても、今回の独立した変換要求として処理する。
前回の応答であることを証明するセッション ID や署名トークンは要求しない。

一方、今回の要求内の整合性は検証する。

- 各文節の読みを連結した結果は、全体の `reading` と一致すること。
- 確定済み文節の `candidates` は文字列1件だけであること。

不整合のある要求はエラーとする。確定候補について、前回のサーバー応答に含まれていた
候補かどうかの照合はしない。
指定された文節境界を処理できない場合も、黙って自動分割に戻さずエラーを返す。

## エラーと処理制限

エラー本文は `ErrorResponse` の JSON とする。
`details` は任意で、入力エラー（400）のときに、不正な項目の位置（`field`）と理由（`reason`）を返す。

```json
{
  "message": "invalid request",
  "details": [
    {"field": "segments[1].candidates", "reason": "confirmed segments require exactly one non-empty candidate"}
  ]
}
```

| HTTP ステータス | 意味 |
| --- | --- |
| 400 | 不正な JSON、フィールド型、空の読み、確定候補、要求内の文節の不整合。 |
| 413 | 要求本文が 1 MiB を超える。 |
| 415 | Content-Type が `application/json` ではない。 |
| 422 | Mozc が指定境界を実現できない（Mozc が読みを書き換えた場合を含む）。 |
| 500 | 想定外のエラー。 |
| 502 | Mozc の応答が不正（候補がないなど）。 |
| 503 | Mozc に接続できない、または変換に失敗した。 |
| 504 | 変換処理の15秒の期限超過・キャンセル。 |

読みと文節の読みは空文字列を許容しない。
確定済み候補も空文字列を許容しない。

## 未確定事項・今後の検討事項

- 本文サイズ・処理期限以外の、読みの長さ・文節数の上限。
- 候補数の上限（`max_candidates`）を超えた候補の扱い。
  文節に照会用のキーを付けて、ページングで残りを返す案がある。実機で使ってから決める。
- 任意の前後文脈を要求に含める際の具体的なフィールドと形式。
  共有会話では `context` を毎回送る案があるが、確定した JSON 形式はまだない。
- 確定文字列を周囲の候補順位に反映する方法。
  現在は全体の読みと文節境界で変換し、確定文節の候補をクライアントの指定で維持する。
  任意の確定文字列を Mozc の文脈に注入する処理は行わない。
- 共有会話には文節長の配列による指定案もあるが、本書の再要求例は、
  この会話で具体化した文節オブジェクトの配列を用いる。
  文節長の配列を別形式として受け付けるかは未確定とする。
